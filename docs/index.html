Project

Change-Gate

It looks at a proposed change to live software, works out how dangerous it is, and either lets it through, hands it to a person, or blocks it.

For the engineer on call who has to answer that at twenty to two in the morning.

Recorded run, 2026-07-27, commit 0493941

At 01:40, a safe change and a disaster look identical

A request lands: turn on the switch called checkout_v2 in the live shop. To answer well you would need to know what else falls over if the gateway falls over, whether that service broke last week, whether the company is inside a no-changes period, and whether the person asking is even allowed to touch the live system. Those four answers live in four places, and none of them are open at 01:40. So the change gets approved, because saying no costs more than saying yes.

Before

A person answers from memory, at whatever hour the request arrives. The reasoning goes in a chat message nobody can find again, and there is no record of what was known at the time.

After

The same four checks run the same way every time, on every request, at any hour. The answer is filed together with the numbers that produced it.

The gate is only as good as four numbers somebody picked by hand

    

      
Written down so nobody has to find out the hard way

      
Every line here is checkable against a file in the repository.

      
    
        
        
  • It has never been pointed at a real company's changes. Everything you just watched runs on
        the made-up sample in src/change_gate/data/seed.py: 2 companies, 8 services, 5 change requests.
    • 
        
        
  • The four weights and the two cut-off scores were picked by hand and written into the settings
        file. Nobody fitted them to a record of which changes actually caused outages, so a change can
        score 29.9, land under the cut-off of 30, and go straight through.
    • 
        
  • The no-changes period is the only absolute block. Everything else is a number against a
        threshold, so the gate is exactly as good as the numbers somebody chose.
    • 
        
  • Keeping one company's data away from another's, and checking that a caller really is who they
        say, both need a database and a login server running in the background. The run on this page uses
        the offline path only, so it shows the deciding, not the separating.

Six steps, and each one is a file you can open

    

      Written in Python. The parts that decide whether something is safe are plain functions with no
      moving parts, which is why the same request always gives the same answer.
    

    
    
      
  1. Read the request, the settings, the map of which service leans on which, the calendar of frozen
      dates, and anything that broke recently.
      tools.py
    2. 
      
  2. Check the request makes sense and that the person asking is allowed to touch that environment.
      decision.py
    3. 
      
  3. Work out four numbers about it, weight them, and add them into one score out of 100.
      risk.py
    4. 
      
  4. Check whether the hours it asked for overlap a frozen stretch of calendar. If they do, that
      beats the score.
      risk.py, freeze_collision
    5. 
      
  5. Turn all of that into one of three answers: let it through, hand it to a person, or block it.
      decision.py, decide
    6. 
      
  6. Write the answer to a running record, each entry sealed with a code worked out from the entry
      before it.
      audit.py
    7. 
    

    

      The six steps are wired together in
      agent/graph.py,
      using LangGraph, a library for wiring steps together. If a step cannot get the data it needs, the
      run is marked incomplete and an approval is downgraded to a hand-over, never the reverse.
